# 项目宪章

状态：Accepted

## 定位

FurinaChronicle 当前是一个本地优先的原神个人历史档案工具。官方服务负责提供当前可查询的数据；FurinaChronicle 在用户授权下尽可能记录能够可靠取得和长期保存的账号数据，使其在几年后仍可查看、查询、导出、迁移和分析。

共享身份、可移植性和领域基础设计允许未来按实际需求接入其他游戏，但共享架构首先服务已经实施的具体需求，不以建设面向任意游戏的通用历史数据平台或未来同步框架为产品目标。

## 核心目标

- 持续保存可可靠取得的抽卡、角色、武器、挑战、成就、背包、资源流水、便签状态和游玩记录等数据；不承诺恢复已不可取得的历史。
- 各领域独立管理规范化事实、历史、查询和展示，不依赖 Chronicle 才具有价值。
- 清楚区分官方证据、外部导入、本地观察、用户输入和派生结果。
- Windows 与 Android 之间的文件级数据迁移和语义一致是核心需求；未来平台按实际需要扩展。
- 对有社区标准的数据优先实现标准格式的完整导入和导出。
- 提供领域级机器可读导出、分类及完整备份，以及 Markdown、文本、表格等人类可读导出。用户应能脱离当前 UI 查看、归档和分析自己的数据；人类可读输出可以不可重新导入。
- Chronicle 筛选、组合和叙事展示已有领域事实，不是事实来源，也不是领域唯一的查看或导出渠道。
- 无服务端、无账号和离线时，核心档案能力仍可使用。

## 游戏范围与扩展

- 当前产品、路线图和领域验收以原神为范围。
- 共享身份必须能够区分游戏，可移植数据应保留所属游戏语义；未来游戏不得因为 UID 或显示名称相同而与原神角色错误合并。
- 未来游戏按照实际需求逐步接入，通过独立 Provider、Codec、适配器或领域实现扩展。
- 只有实际实施证明语义相同的能力才进入共享基础；当前 Phase 不为未实施游戏预先统一所有角色、装备、挑战、背包或资源模型。
- 首个潜在扩展为《崩坏：星穹铁道》，预计优先复用 UIGF 和现有导入导出基础接入抽卡记录；这不是当前 Phase 的交付承诺。

## 跨文档设计原则

| 原则 | 约束 |
|---|---|
| 领域自治 | 各领域自行管理事实、历史和用例；Chronicle Contributor 不是领域成立的必要条件 |
| 数据优先 | 先可靠保存能够取得的数据，再建设统计与综合展示；未知时间、来源、顺序和完整性不得伪装成精确事实 |
| 开放导出 | 有通用标准时优先标准；Furina 机器可读格式服务标准未覆盖的数据、迁移和备份；人类可读格式服务外部查看与分析 |
| Chronicle 派生 | Chronicle 是确定性、可重建的读取投影；Profile、颗粒度与分页不反向塑造或修改领域事实 |

具体作用域和未来游戏扩展边界由 [ADR 0011](../decisions/0011-domain-first-product-scope.md) 记录，领域能力清单见 [架构总览](../architecture/OVERVIEW.md)。没有进入 Chronicle 的领域数据不因此成为次要或临时数据。

## 核心价值

1. 数据首先属于用户。
2. 历史可追溯比短期便利更重要。
3. 不确定性必须显式表达。
4. 可迁移性高于对当前数据库结构的便利依赖。
5. 失败不得破坏已经持久化的用户数据。

## 维护方式

项目目前由单人主维护。流程应优先帮助维护者和 Agent 保持长期一致性，而不是模拟大型团队审批。不可逆或长期兼容决策使用简短 ADR；普通内部实现不要求额外审批文件。

每个工作包应可独立测试和审查。遇到边界问题先判断：“这个决定如果以后再做，会不会使今天已经保存的数据无法解释？”如果不会，也不影响跨端身份、公开格式兼容或数据安全，应下放到对应领域或后续 Phase。

## 服务端定位

服务端是可选扩展，不是客户端核心的前置条件。未来可以提供：

- 云端备份；
- 多设备增量同步；
- 公共元数据；
- 用户主动参与的大规模抽卡或挑战统计。

这些能力必须保持独立授权和独立接口。统计服务不得默认读取私人备份，客户端也不得因服务端不可用而失去本地档案能力。

自动云同步属于未来可选能力，不得反向要求当前领域模型提前实现设备游标、分布式冲突协议或完整 ChangeJournal。
