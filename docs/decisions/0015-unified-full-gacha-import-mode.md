# ADR 0015：统一 Gacha 全量导入模式

状态：Accepted

日期：2026-10-14

## 背景

抽卡页原有“全量刷新”开关只明确影响官方接口刷新；UIGF、提瓦特小助手、
兼容 JSON 和 Furina Portable 仍固定采用 PreserveExisting 或 AddOnly。用户在同一页面
选择全量模式时，不同入口却具有不同的同记录处理方式，容易造成错误理解，也无法用
可信外部文件纠正已有的不准确事实。

ADR 0014 对普通导入采用保守策略。本 ADR 根据维护者的新决定，在保留该默认行为的
同时，为用户显式开启的全量模式增加统一覆盖语义。

## 决定

- 抽卡页提供统一的“全量导入模式”。关闭时保持各入口原有的增量、仅补充或 AddOnly
  行为；开启时作用于该页所有刷新和导入入口。
- SToken、手工 URL 和 Windows 网页缓存刷新在全量模式下请求全部可得分页，并以
  官方响应覆盖同一稳定记录。
- UIGF、提瓦特小助手和兼容 JSON 在全量模式下，以来源记录覆盖同一账号、同一
  ExternalRecordId 的已有事实。
- Furina Portable 在全量模式下允许预览并覆盖同一稳定记录；默认模式仍为严格
  AddOnly。规划后目标事实发生变化时必须拒绝应用，不得覆盖未经过预览的状态。
- 全量模式只覆盖来源中明确存在的稳定记录，不删除来源缺失的本地记录，也不据此
  声明来源数据完整。
- 覆盖必须通过现有原子 ChangeSet 写入，并保存 before/after Revision；符合撤销条件时
  继续产生 Undo 材料。不得绕过 Tombstone、容量确认、OperationId 幂等或账号归属校验。
- 自动来源命中活动 Tombstone 时仍按 ADR 0014 抑制；Portable 仍需用户逐次明确确认
  重引入。全量模式本身不构成永久删除记录的恢复授权。
- 界面在执行覆盖型文件导入前必须明确提示覆盖语义。结果应区分新增、覆盖和保留数量。

## 后果

- 一个开关在所有抽卡获取入口中具有一致含义，同时默认操作仍保持保守。
- 用户可以用可信 UIGF、提瓦特小助手或 Portable 数据纠正已有错误记录，旧值仍能通过
  Revision 审计，并在策略允许时撤销。
- Portable 规划需要区分 Add、Replace、Skip 与 Conflict，并保存被预览目标事实的稳定
  指纹或等价前置条件，避免过期计划覆盖并发变化。

## 验证要求

- 覆盖三种刷新来源、UIGF/小助手、兼容 JSON 和 Portable 的默认与全量模式。
- 证明全量模式可以覆盖同记录但不会删除来源缺失记录。
- 证明覆盖产生 Revision，撤销后恢复原事实。
- 证明 Portable 规划后的目标变化会返回 Conflict，且整个包保持原子。
- 证明 Tombstone、容量确认和 OperationId 重试行为不因全量模式弱化。
