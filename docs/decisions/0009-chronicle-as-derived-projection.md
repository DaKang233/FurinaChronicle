# ADR 0009：Chronicle 作为派生投影

状态：Accepted

确认日期：2026-10-02

## 背景

FurinaChronicle 最终需要把抽卡、成就、挑战、角色与武器状态、背包、资源流水、便签和游玩会话组合为长期时间线。这些领域的时间精度、来源可信度、数据生命周期和更新方式不同。同时，应用还需要记录导入、覆盖、撤销和删除等档案操作。

如果把所有内容直接写入一个通用 `TimelineEvents` 真相表，将产生重复事实、领域字段丢失、修订难以同步和游戏事件与应用操作混淆的问题。

## 选项

1. 所有领域直接写入统一时间线事实表。
2. UI 临时拼接所有领域，完全不定义共享时间线契约。
3. 各领域保存规范化事实，通过统一贡献者契约产生可重建的 Chronicle 投影；档案操作历史独立存在。

## 决定

采用选项 3。

- 规范化领域记录是事实来源；
- `ChronicleEntry` 是面向查询、UI 和报告的派生投影；
- 游戏历程与档案操作历史分别建模；
- 时间线支持瞬时、确定区间和不确定区间；
- Chronicle 可以有多个面向用途的时间线 Profile；主时间线只展示重要节点，领域时间线可以按用户选择提高颗粒度；
- 未进入某个默认 Profile 的事实仍保留在规范化领域数据中，不得因为默认 UI 隐藏而丢弃；
- 数据量需要时可以建立版本化、可丢弃、可重建的物化索引；
- 可移植数据集和同步以规范化领域记录为主，不依赖时间线索引。

## 原因

- 保留不同数据域的完整语义与来源证据；
- 防止 `ImportedAt`、`ObservedAt` 被误认为游戏事实发生时间；
- 允许新增领域而不迁移一张不断膨胀的万能表；
- 允许修订、撤销、删除和元数据更新后重建投影；
- 适合本地优先、跨平台导出和未来可选同步。

## 后果

- 每个进入 Chronicle 的领域需要实现贡献者和测试；
- 贡献者负责产生候选事件，Profile 负责决定默认可见性和展示颗粒度，二者不得混为同一条存储规则；
- 跨域查询可能需要归并多个有序结果，数据量扩大后可能引入物化索引；
- 时间范围、精度、来源、置信度和稳定分页游标必须成为共享基础类型；
- UI 不得依赖某个领域的数据库行结构。

## 迁移影响

现有抽卡统计、历史和日历可以继续使用。Phase 8B 为现有 `GachaRecord` 补充共享时间与来源语义时必须保持 UIGF 导入导出兼容，并通过迁移或默认来源映射处理旧记录。

角色/武器状态与挑战记录应在共享基础类型完成后成为首批新领域，用不同的时间模型验证该决策。正式跨域时间线 UI 不属于第一批迁移要求。

主时间线、角色时间线、武器时间线和挑战时间线的产品边界由 [ADR 0010](0010-curated-multiple-chronicle-timelines.md) 与 [Chronicle 产品需求](../specifications/CHRONICLE_PRODUCT_REQUIREMENTS.md) 进一步约束。

## 测试要求

- 同一规范化记录重复投影得到相同 `EntryId` 和排序键；
- 游戏事实时间与导入、观察、抓取时间不会互相替代；
- 瞬时、区间和不确定区间均可稳定排序和分页；
- 多账号档案查询不丢失账号归属；
- 投影索引删除后可以从规范化记录重建；
- 修订、撤销和不可逆删除后的投影与当前有效事实一致；
- 导出不依赖 Chronicle 索引即可完整恢复领域数据。
